# План: бюджет дня и перерасход на экране «Статистика» родителя

Дата: 2026-08-04. Макет: `docs/ui-concepts/statistics-budget/statistics-budget-mockup.html`.

## Зачем

Родитель видел «Лимит: 3 ч 00 мин · исчерпан» при выданном на сегодня бонусе в 1 час и экранном
времени 4 ч 53 мин. Две проблемы разом:

1. **Бонус не учитывался** — прямой баг. `StatisticsViewModel` берёт голый лимит
   (`policyRepository.dailyLimits.first().limitFor(...)`), тогда как весь остальной код считает
   бюджет как `лимит + бонус`: `ObserveLimitStateUseCase` (сам enforcement), `TodayViewModel`,
   `ChildTodayStatsViewModel`, `SyncRepositoryImpl.applyDailyBlock`. Родительская «Статистика» —
   единственное место, которое расходится с реальным поведением приложения, причём в обе стороны
   («осталось» тоже занижалось).
2. **Расход больше бюджета выглядел как сбой.** `ScreenTimeTracker` начисляет время, пока экран
   включён, разблокирован и не закрыт нашим блокирующим UI — включая «Всегда доступные»
   приложения и лаунчер. Оверлей блокировки смахиваемый намеренно (чтобы ребёнок мог позвонить),
   поэтому после исчерпания бюджета время продолжает капать. Это ожидаемое поведение, но карточка
   подавала две цифры как одну шкалу, и родитель делал вывод «телефон должен был заблокироваться
   53 минуты назад».

Перерасход при этом — **ценный сигнал**, а не мусор: он показывает, сколько ребёнок пользовался
телефоном после блокировки.

## Что делаем

### Карточка «Экранное время сегодня»

```
Экранное время сегодня
4 ч 53 мин
[▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓|▒▒▒]
Бюджет дня 4 ч 00 мин   ·   3 ч лимит + 1 ч бонус
Сверх бюджета 53 мин — доступны только разрешённые приложения
```

Состояния:

| Ситуация | Шкала | Подпись бюджета | Строка состояния |
|---|---|---|---|
| Лимит есть, время осталось | заполнение `used / budget` | «Бюджет дня X» | «Осталось Y» (primary) |
| Лимит есть, перерасход | бюджетная часть + сегмент перерасхода | «Бюджет дня X» | «Сверх бюджета Y — доступны только разрешённые приложения» (tertiary) |
| Бонуса нет | — | без расшифровки «лимит + бонус» | — |
| Бонус есть | — | «Бюджет дня X · A лимит + B бонус» | — |
| Лимит 0 | шкала целиком перерасход | «Бюджет дня 0 мин · доступ закрыт» | как при перерасходе |
| Лимита нет | шкалы нет | «На сегодня лимит не задан» | — |

Цвет перерасхода — **золотой** (`tertiary`: `#E0A73C` тёмная / `#B07D1E` светлая). Красный
`DangerAccent` в приложении означает опасное действие и на статистике читался бы как сбой.

### График «Последние 7 дней»

- Пунктирная риска бюджета у каждого столбика: **лимит того дня недели + бонус, выданный в тот
  день**. Линия ступенчатая, а не одна прямая, — лимиты задаются по дням недели, а бонусы привязаны
  к дате. При одинаковых лимитах выглядит ровной.
- Часть столбика выше риски красится в цвет перерасхода.
- Легенда под графиком: «в пределах бюджета» / «сверх бюджета» / «бюджет дня».
- **Масштаб**: сейчас `maxSeconds` — максимум по факту использования. Если бюджет выше всех
  столбиков, риска ушла бы за верх графика. Берём `max(использовано, бюджет)` по всем дням.

## Реализация

### `StatisticsViewModel`

- Добавить зависимость `BonusRepository`.
- Бонусы за все 7 дней брать из `bonusRepository.observeAll().first()`, отфильтровав бонусы
  телефона (`packageName` пустой) — отдельный метод в репозитории не нужен. Исторические бонусы
  сохраняются: сервер хранит policy как непрозрачный JSON и старые записи не чистит.
- `DayUsage` получает поле `budgetMinutes: Int?` (лимит дня + бонус того дня; null — лимита нет).
- В `StatisticsUiState` вместо `todayLimitMinutes` — `todayLimitMinutes` + `todayBonusMinutes`,
  чтобы UI мог показать расшифровку «лимит + бонус». Бюджет считается в UI как их сумма.

### `StatisticsScreen`

- `TodayCard`: шкала (двухсегментный `Row` в `clip(RoundedCornerShape)`), строка бюджета,
  строка состояния. Логику ветвления вынести в приватную функцию, возвращающую sealed-состояние —
  иначе `TodayCard` превратится в лестницу `if`.
- `WeekChartCard`: риска бюджета и двухцветный столбик; `maxSeconds` с учётом бюджета; легенда.
- Все тексты — в `strings.xml`, ничего не хардкодим.

### Тесты

`StatisticsViewModel` сейчас не покрыт (в `core/src/test` только usecase-тесты, VM живёт в `:app`).
Расчёт бюджета и перерасхода вынести в чистую функцию в `:core` (рядом с `ObserveLimitStateUseCase`)
и покрыть юнит-тестами: бонус учитывается, перерасход считается, лимит 0, лимита нет.

## Проверка

1. `./gradlew :core:test :app:assembleDebug`.
2. На родительском эмуляторе, обе темы:
   - бонус выдан, время осталось → «Бюджет дня X · A лимит + B бонус», «Осталось Y»;
   - бонус выдан, перерасход → сегмент перерасхода и строка «Сверх бюджета»;
   - бонус отменён (`clearBonus`) → бюджет возвращается к голому лимиту;
   - лимита на сегодня нет → «На сегодня лимит не задан», шкалы нет;
   - на графике риска сегодняшнего дня выше остальных ровно на выданный бонус.

## Продолжение от 04.08.2026: два хвоста

### 1. История бонусов (правка первоначального диагноза)

Утверждение «policy-документ растёт бесконечно» оказалось **неверным**: в `currentLocalDocument()`
в документ уходили только сегодняшние бонусы, а `applyDocument` делает `replaceAll` — то есть
локальная таблица схлопывалась до сегодняшних при каждом pull. Расти было нечему.

Зато вскрылась настоящая проблема: **истории бонусов не существовало нигде**, и риска бюджета за
прошлые дни на графике рисовалась по голому лимиту дня недели. Точен был только сегодняшний день.

Решение — возить в документе бонусы за `BonusRepository.HISTORY_DAYS` (14) дней и чистить локально
всё старше. Период вдвое больше показываемой недели, документ остаётся ограниченным.

- `BonusDao.deleteOlderThan` + `BonusRepository.deleteOlderThan`;
- фильтр в `currentLocalDocument()` — по `bonusHistoryCutoff()`, а не по «сегодня»;
- чистка в начале `parentSyncLoop`, до первого push, чтобы старьё не уехало на сервер.

Данные за прошлые дни появятся не задним числом: риски станут честными для дней, начиная с этой
версии.

### 2. «Всегда доступные» не расходуют дневной лимит

`shouldBlock` выводил whitelist и `alwaysAllowed` из-под общего лимита, а `ScreenTimeTracker`
начислял время всем подряд: час разговора по телефону съедал час игрового времени.

Решение — считать это на уровне **учёта**, а не расчёта, чтобы не заводить второй счётчик и не
трогать схему БД и API:

- `ScreenTimeTracker` начисляет пер-app время **всем** приложениям, а общий счётчик пополняет
  только теми, что расходуют лимит;
- правило вынесено в `:core` чистой функцией `countsTowardsDailyLimit` рядом с `shouldBlock` и
  покрыто тестами, включая проверку согласованности этих двух функций;
- `alwaysAllowed` (лаунчер + само KidGuard) вынесено из `BlockingController` в общий
  `AlwaysAllowedPackages`, потому что то же множество теперь нужно трекеру.

Следствие: `UsageRepository.screenTimeSeconds` меняет смысл на «время, расходующее лимит», а «всё
экранное время» = сумма по `appScreenTimeByPackage`. Это же значение уходит на сервер как
total-запись, поэтому родитель получает обе величины без изменений API.

UI после правки:

- крупная цифра «Экранное время сегодня» — всё экранное время (совпадает с суммой блока
  «По приложениям»);
- шкала, бюджет и перерасход — по времени, расходующему лимит;
- новая строка «Вне лимита X — «Всегда доступные» и домашний экран», иначе цифры не сходятся;
- график переименован в «Расход лимита за 7 дней»: он строится по лимитному счётчику, и без
  подписи столбик за сегодня расходился бы с крупной цифрой;
- детские экраны («Сегодня» и статистика) — та же логика: кольцо и остаток по лимитному счётчику,
  карточка «Сегодня» и крупная цифра по всему экранному времени.

**Историю это не переписывает:** дни до обновления считались по-старому, их лимитный расход
завышен на время «Всегда доступных» и лаунчера. Выровняется за неделю.
