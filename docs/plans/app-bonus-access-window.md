# Дополнительное время конкретному приложению

**Статус:** реализовано, проверено на эмуляторах; ожидает приёмки Володей
**Заведён:** 2026-09-08

## Задача

Родитель должен иметь возможность открыть ребёнку **одно конкретное приложение**, когда общий
дневной лимит уже исчерпан, — не снимая блокировку со всего телефона (для этого есть бонус
телефона на экране «Дневной лимит»).

Блок «Дополнительное время» в bottom-sheet приложения должен показываться **всегда**, независимо
от того, задан ли приложению личный лимит.

## Что уже готово и трогать не нужно

- `BonusRepository.addBonus(date, packageName, minutes)` / `clearBonus` / `appBonusMinutes` —
  бонусы по приложениям поддержаны с вехи 3Б.
- `AppLimitsViewModel` отдаёт `bonusMinutes` для **каждого** приложения и умеет выдавать и
  отменять бонус. Правок не требует.
- **Сервер правок не требует вообще** — `policies.data` для него непрозрачный TEXT
  (`policyService.js`: «не парсит и не валидирует структуру»).
- Канал статистики ребёнок→родитель (`pushUsage`) уже возит записи вида `пакет → секунды`
  с маркерными псевдопакетами — новый счётчик поедет по нему же.

## Почему одного `if` в UI недостаточно

Видимое условие — `AppLimitsScreen.kt:219`. Под ним три слоя, каждый гасит фичу сам по себе:

1. **`ObserveAppLimitStateUseCase.kt:44`** — `if (limitMinutes == null) return LimitState.NoLimit`.
   Бонус отбрасывается: кнопка нажмётся, запись уйдёт, состояние не изменится.
2. **`BlockingDecision.shouldBlock`** — нет ветки «у приложения есть персональный пропуск».
   Пункт 5 (общий лимит `Expired`) сработает раньше.
3. **`VpnPolicy.vpnDisallowedFor`** — при исчерпанном лимите поднимается blackhole-VPN, обходят
   его только whitelist и сам KidGuard. Иначе приложение открылось бы **без интернета**.

## Принятые решения (Володя, 08.09.2026)

1. **Интернет на время окна — даём.** Приложение с активным окном обходит VPN наравне с whitelist.
2. **Блок виден всегда**, не прячется до исчерпания лимита. Прятать нельзя: `pushUsage` идёт на
   15-минутном тике (`SyncRepositoryImpl.kt:294`), и родитель узнавал бы об исчерпании с
   задержкой — блока не было бы ровно в тот момент, ради которого делается фича. Плюс при
   незаданном дневном лимите исчерпания не бывает никогда, а приложение со своим личным лимитом
   всё равно блокируется.
3. **Окно стартует по факту, а не с момента выдачи.** Выданное время не должно утекать вхолостую,
   если ребёнок приложением не пользуется.

### Как это реализуется (способ Б)

Расход окна = **время в приложении, накопленное при исчерпанном общем дневном лимите**.

Рассматривался и отвергнут способ с настенными часами + `startedAt`: момент старта пришлось бы
возвращать родителю, а бонусы едут в policy-документе, который однонаправлен (ребёнок при pull
делает `replaceAll` и затирает своё локальное). Способ Б обратной синхронизации состояния не
требует — счётчик едет существующим usage-каналом. Отпадают `expiresAt`, `startedAt`, провайдер
времени с анти-отмоткой и периодический тик: состояние меняется от накопления расхода, а поток
usage реактивный.

## Архитектура

Личный лимит и окно доступа — две независимые механики в одной записи бонуса:

| | приложение с личным лимитом | без личного лимита |
|---|---|---|
| прибавка к личному лимиту | да, как сейчас | лимита нет — не применимо |
| окно доступа мимо общего лимита | да | да |

**`ObserveAppLimitStateUseCase.calculate` не трогаем.**

### Новый счётчик

`app_screen_time` получает колонку `bonusSpentSeconds` — **параллельный** счётчик, а не третий
приёмник тика. Пока окно активно, тик уходит и в обычный `appBucket`, и в `bonusSpentSeconds`.

Почему параллельный, а не вместо `appBucket`: у приложения со своим личным лимитом бонус
одновременно продлевает этот лимит (через `minutes`) и открывает окно. Если бы тик уходил только
в окно, личный лимит перестал бы тратиться, и две механики разъехались бы. При параллельном счёте
они кончаются согласованно.

`bonusSpentSeconds` **не входит** в `appTotalScreenTimeByPackage` — иначе время задвоилось бы в
статистике. Трогать total и bucket-логику не нужно вовсе.

**Дневной перерасход при активном окне не растёт:** `dailyBucket = null`, как для белого списка.
Иначе разрешённое родителем время попадало бы в `overrunSeconds` и показывалось родителю как
нарушение — время, которое он сам и выдал.

Пропуск активен, пока `bonusMinutes - bonusSpentSeconds / 60 > 0`.

### Новое правило доступа

`shouldBlock` получает `hasBonusAccessPass: Boolean` и ветку **между п.4 (whitelist) и п.5**:

```
1. alwaysAllowed              → доступно
2. blockedApps                → блокируем   (запрет родителя бьёт и пропуск)
3. личный лимит Expired       → блокируем   (пропуск НЕ бьёт личный лимит)
4. whitelist                  → доступно
5. активный пропуск           → доступно    ← НОВОЕ
6. общий лимит Expired / учёба→ блокируем
7. иначе                      → доступно
```

**Пропуск стоит после п.3 намеренно.** Если у приложения есть личный лимит и он исчерпан, бонус и
так продлевает этот лимит через `minutes`, обычным путём. Ставить пропуск выше значило бы дать ему
обходить личный лимит в обход учёта времени.

**«Время учёбы» и «Время сна» пропуск не снимает.** Расписание — осознанное «сейчас телефон
нельзя»; открывать его точечным бонусом было бы неожиданно. При необходимости — отдельным решением.

5. Проверка на двух эмуляторах: исчерпать общий лимит, выдать время, убедиться, что приложение

## Крайние случаи

- **Общий лимит не исчерпан** — бонус лежит невыработанным, время не тратится. Ровно то поведение,
  которого мы хотели: выдать можно заранее, утечь оно не может.
- **Полночь** — расход окна привязан к дате, как и весь usage; бонус живёт до конца своего дня.
- **Бонус телефона** окна не получает: у него семантика минут экранного времени, менять её в этой
  работе не нужно.
- **Отмена бонуса** родителем гасит пропуск немедленно — блокировка возвращается на следующем
  пересчёте. **`clearBonus` обязан обнулять и `bonusSpentSeconds`**: иначе выданные повторно
  минуты сразу гасятся старым расходом (выдали 15 → израсходованы → отменили → выдали снова 15,
  остаток `15 − 15 = 0`), и приложение не откроется.
- **Повторное продление без отмены** работает суммированием: `15 + 15 = 30` против потраченных
  15 → остаётся 15. Число повторов не ограничено.
- **Доставка выдачи ребёнку мгновенна существующим каналом** и доработки не требует: бонусы
  входят в push-снапшот и в `combine` родительского цикла (`SyncRepositoryImpl.kt:178`), дальше
  WS `PolicyChanged` → `pullAndApply` на детской стороне. Замер 07.09.2026 — 10,5 секунды от
  правки родителя до снятия оверлея. 15-минутный тик здесь ни при чём, он лишь страховка.
- **Возврат блокировки по исчерпании окна** происходит на ближайшем тике трекера — точность до
  периода тика, ребёнок может получить неполную лишнюю минуту. Приемлемо.
- **Пересборка VPN** при выдаче и при истечении окна рвёт активные соединения приложения
  (смена disallowed-набора пересоздаёт туннель). Для переписки незаметно, звонок может
  переподключиться. Отдельно чинить не планируем.

## Что выяснилось при реализации (09.09.2026)

### Ограничение: родитель не видит израсходованный остаток

План предполагал, что расход окна «поедет родителю существующим usage-каналом». Канал
(`pushUsage`) действительно есть, но **приёмной стороны у родителя нет**: `SyncRepositoryImpl`
наполняет локальную usage-БД только на детском устройстве, а статистику родитель запрашивает
разово через `getChildUsage` и в Room не кладёт. То есть `usageRepository.appBonusSpentByPackage`
на родительском телефоне всегда пуст — как и `appScreenTimeByPackage` (это существующее поведение,
не следствие этой работы: строка «Сегодня: 0 из 30 мин» у родителя всегда показывает ноль).

**Как ведёт себя UI сейчас:** остаток равен выданному, поэтому показывается обычная строка
«Сегодня выдано: +15 мин» без приписки об остатке. Деградация корректная — экран не врёт, просто
не показывает расход. Логика остатка (`bonus_active_left` / `bonus_active_spent`, бейдж в списке)
написана и заработает сама, как только расход начнёт доезжать.

**Что нужно, чтобы доделать** (отдельной задачей, к этой фиче не критично): провезти
`bonusSpentSeconds` в `UsageEntryDto` под маркерным псевдопакетом по образцу `OVERRUN_PACKAGE`
(`__overrun__`) и либо наполнять локальную usage-БД родителя при pull, либо читать остаток в
`AppLimitsViewModel` через `getChildUsage`. Точность в любом случае будет с задержкой до 15 минут:
статистика ребёнка уезжает на общем тике.

### Тестов миграций в проекте нет

`KidGuardDatabase` обещает `MigrationTestHelper`, но ни одного теста миграции не заведено.
Миграция 13→14 проверена иначе — обновлением поверх **живых баз v13** на обоих эмуляторах:
`user_version` стал 14, 64 строки истории на детском устройстве сохранены, падений нет.

### Что проверено на устройствах

| Проверка | Результат |
|---|---|
| Блок виден у приложения **без** личного лимита | да, с подписью «Откроет это приложение, когда общий дневной лимит закончится» |
| Выдача доезжает до ребёнка | ~12 секунд (WS), без 15-минутного ожидания |
| Время не тратится, пока общий лимит цел | `bonusSpentSeconds` = 0 при выданных 15 минутах |
| Приложение открывается при исчерпанном лимите | да, блокировки нет |
| Окно списывается временем в приложении | `finkeeper: seconds=75, bonusSpent=75` |
| Дневной перерасход от этого времени НЕ растёт | лог: «дневной вне лимита»; +15 сек перерасхода дала шторка, не приложение |
| Без бонуса то же приложение блокируется | `Блокировка активна (причина=LIMIT_EXPIRED)`, выкинуло на лаунчер |
| Отмена гасит пропуск и обнуляет расход | `bonusSpentSeconds` 75 → 0, обычный расход 255 сек сохранён |
| Повторная выдача после отмены открывает снова | да — ради этого и нужен сброс расхода |

### Замеченное попутно, не чинилось

Уведомление VPN гласит «Время на сегодня вышло — интернет доступен только KidGuard». При активном
пропуске это уже неточно: интернет есть и у открытого приложения. Текст не трогал — правка вне
объёма этой работы.
