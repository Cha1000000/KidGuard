# Точный учёт времени и возврат контроля после убийства

Дата: 06.09.2026. Ветка первой задачи: `feature/usage-attribution`.

Продолжение [control-self-healing.md](control-self-healing.md). Тот план исходил из диагноза
«виновата кнопка „Очистить всё“, лечится замком карточки». Боевая диагностика 06.09 показала, что
**замок не защищает**, и попутно вскрыла отдельный баг учёта экранного времени. Этот документ
фиксирует новые факты и три задачи, которые из них следуют.

### «Очистить всё» на HiOS работает в две фазы

```
11:55:11.0–11:55:11.2   REMOVE TASK, cleanType:oneKeyClean   → 4 приложения (у них есть карточка)
11:55:11.2–11:55:12.8   STOP APP, "fully stop … by user request" → 14 приложений (весь остальной фон)
```

KidGuard попал во **вторую** фазу. Замок карточки влияет только на первую. Проверено по всей
истории телефона: **из 152 записей `STOP APP` ни у одной нет `recentTaskInfo`** — фаза 2 бьёт
именно по тем, у кого карточки в списке недавних нет.

05.09 приложение пережило четыре очистки (12:47, 13:51, 15:27, 16:25) только потому, что в тот день
мы сами его открывали и залоченная карточка висела в recents. Сегодня карточки не было — Олег
KidGuard не открывал.

**Вывод: замок карточки — не защита, а побочный эффект. Он работает ровно до тех пор, пока карточка
есть в списке недавних, а её достаточно смахнуть пальцем.** Вывод от 05.09 («лечится замком»)

## Ответ на предложение: автоматический перезапуск раз в час

Идея (Володя, 06.09): фоновый сервис, который раз в час принудительно поднимает приложение, если
его убили, чтобы не ждать реакции родителя.

**Реализовать это нельзя, и вот почему — по пунктам.**

1. **Изнутри самого приложения — невозможно.** После force-stop пакет уходит в stopped-состояние:
   ему не доставляются broadcast'ы, не срабатывают `AlarmManager` и `WorkManager`, не помогает
   always-on VPN. Проверено экспериментом 05.09: `force-stop` → `install -r` → через 70 секунд
   процесса нет, сервисов ноль, разрешение не вернулось. Сервис, который должен перезапускать
   приложение, умирает вместе с приложением — он и есть первая жертва.

2. **Отдельное приложение-сторож (второй APK) — не выживет.** Та же «Очистить всё» убила 18
   приложений одним нажатием, и среди выживших нет ни одного пользовательского пакета (см. выше).
   Сторож умрёт в той же волне, что и подопечный, — скорее всего в той же секунде.

3. **Push тоже не разбудит.** FCM-сообщение доставляется broadcast'ом, а stopped-приложение
   broadcast'ы не получает. Это то же самое ограничение.

4. **Единственные способы вернуть приложение к жизни** — ручной запуск и перезагрузка телефона
   (перезагрузка снимает stopped-состояние, проверено). Автоматизировать ни то, ни другое обычному
   приложению нечем.

Полностью закрыть дыру может только Device Owner (`setUserControlDisabledPackages` запрещает
force-stop) — он требует сброса телефона к заводским настройкам и снятия Family Link. Володя
06.09 решил: **сброс не рассматриваем**.

**Что из идеи реализуемо и переносится в задачи ниже.** Здравое зерно в предложении — «родитель не
должен быть единственным механизмом восстановления». Раз поднять себя мы не можем, делаем две
вещи: (а) убираем выгоду от убийства — время досчитывается задним числом, задача 2; (б) сокращаем
окно незнания — сервер зовёт родителя сам, задача 3.

## Задача 1. Честная атрибуция экранного времени (делать первой)

### Проблема

Учёт приписывает время системной оболочке. Факты:

```
Система за 06.09:  com.android.systemui  totalTimeUsed="00:00"  appLaunchCount=0
Наш учёт за 06.09: com.android.systemui  51 минута
Наш учёт за неделю: com.android.systemui  459 минут  (второе место после Roblox)
```

В нашей базе рядом с ним лежат `com.transsion.aod`, `android`, `ru.yandex.androidkeyboard`,
`com.transsion.dynamicbar` — всё это окна оболочки и клавиатура, а не приложения.

### Причина

`KidGuardAccessibilityService.kt:171`:

```kotlin
if (event?.eventType != AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED) return
val packageName = event.packageName?.toString()?.takeIf { it.isNotBlank() } ?: return
foregroundAppMonitor.update(packageName)   // ← безусловно, чьё бы окно ни было
```

`TYPE_WINDOW_STATE_CHANGED` шлёт **любое** окно, а не только активность: шторка уведомлений, панель
громкости, навбар, AOD, клавиатура, тост. Значение залипает до следующего события.

Подтверждено живьём 06.09 — при пробуждении экрана в лог сразу упало:

```
D/KidGuardA11y: Активное приложение: com.transsion.aod
```

Страховка тоже дырявая: ветка `TYPE_WINDOWS_CHANGED` зовёт `topApplicationPackage()`, а тот
возвращает `null`, если у верхнего окна `root == null` — тогда залипшее значение остаётся.

### Чем это вредит (по убыванию)

1. **Личные лимиты приложений практически не работают.** Треть времени приложения не пишется на
   него — лимит «60 минут на Галерею» отсчитывается часа полтора.
2. **Статистика врёт родителю.** Roblox 06.09: по системе 4:00, у нас 1:34 (плюс 1:41 не считалось,
   пока контроль лежал). Недостающие ~45 минут ушли в systemui.
3. **Дневной лимит подтекает.** По объёму почти верен, но когда залипание случается поверх лаунчера,
   белого списка или самого KidGuard — эти минуты лимит тратить не должны, а тратят. Лаунчер 06.09:
   по системе 9:12, у нас 3:00.

### Решение

Не доверять `event.packageName` вслепую — доверять **типу окна**, от которого пришло событие.

1. **Ветка `TYPE_WINDOW_STATE_CHANGED`:** по `event.windowId` найти окно в `windows` и проверить
   `type == AccessibilityWindowInfo.TYPE_APPLICATION`.
   - прикладное → `foregroundAppMonitor.update(event.packageName)` (как сейчас);
   - не прикладное (`TYPE_SYSTEM`, `TYPE_INPUT_METHOD`, `TYPE_ACCESSIBILITY_OVERLAY`, …) → монитор
     **не трогаем**, вместо этого пересчитываем верхнее прикладное окно.
   - `event.packageName` продолжает питать `detectCriticalScreen` — там нужен именно пакет окна.

2. **Починить определение верхнего прикладного окна.** Сейчас единственный источник имени пакета —
   `window.root?.packageName`, а `root` бывает `null`. Заводим кэш `windowId → packageName`,
   который наполняется из событий прикладных окон; `topApplicationPackage()` сначала смотрит в кэш
   и только потом дёргает `root`. Кэш чистится по `WINDOWS_CHANGE_REMOVED`.

3. **Если прикладных окон нет вообще** (экран блокировки, AOD) — очищать монитор, а не держать
   последнее значение. Нужен `ForegroundAppMonitor.clear()`. Тик учёта при `activePackage == null`
   и так пропускается, так что это просто честная остановка счёта.

### Куда что кладём (Clean Architecture)

- `:core` — чистая функция выбора переднего плана, без Android-типов:
  ```kotlin
  enum class WindowKind { APPLICATION, SYSTEM, INPUT_METHOD, OVERLAY, OTHER }
  data class WindowSnapshot(val id: Int, val kind: WindowKind, val layer: Int, val packageName: String?)
  fun resolveForegroundPackage(windows: List<WindowSnapshot>): String?
  ```
- `:platform` — маппинг `AccessibilityWindowInfo.type → WindowKind`, кэш `windowId → packageName`,
  вызовы монитора.

### Тесты

Юнит-тесты на `resolveForegroundPackage`: только системные окна → `null`; прикладное под системным
→ прикладное; два прикладных → верхнее по `layer`; окно без имени пакета → пропускается.

### Что делать с уже накопленным мусором

459 минут в `app_screen_time` на служебных пакетах. **Историю не переписываем** — восстановить,
какому приложению принадлежало это время, нельзя. После фикса служебные пакеты просто перестанут
появляться. Отдельным вопросом к Володе: прятать ли служебные пакеты на экране статистики за
прошлые дни (косметика, дневные итоги при этом не трогаем).

### Проверка

На телефоне Олега через сутки после установки сверить наш учёт с `dumpsys usagestats`:
`com.android.systemui` в нашей базе должен быть **0**, а время Roblox — сойтись с системным
(с точностью до периодов, когда контроль не работал).

## Задача 2. Досчёт времени, пропущенного мёртвым контролем

### Смысл

Сейчас пока контроль лежит — время не считается вообще, то есть убить приложение **выгодно**:
06.09 Олег получил 101 минуту Roblox бесплатно. Надо сделать так, чтобы это время всё равно
засчиталось при следующем запуске. Тогда обход перестаёт давать выигрыш, каким бы способом он ни
делался, — это работает и против «Очистить всё», и против «Остановить» в настройках, и против
любого следующего трюка.

### На чём держится

`UsageStatsManager` ведёт статистику на стороне системы, и доступ к ней (`GET_USAGE_STATS`)
**переживает force-stop** — в отличие от accessibility, который слетает. Замерено 07.08.2026,
записано в память. Сейчас мы этой статистикой не пользуемся совсем: разрешения нет ни в манифесте,
ни в appops (`cmd appops get ru.homelab.kidguard GET_USAGE_STATS` → `No operations`), тогда как у
Family Link оно есть.

### Что делаем

1. **Разрешение.** `android.permission.PACKAGE_USAGE_STATS` в манифест, проверка через
   `AppOpsManager.unsafeCheckOpNoThrow(OPSTR_GET_USAGE_STATS)`, шаг мастера разрешений с переходом
   в `Settings.ACTION_USAGE_ACCESS_SETTINGS`. Учесть, что наш PIN-перехват настроек не должен
   мешать выдаче.
2. **Ватерлиния.** Хранить `accountedUntil` — момент, до которого учёт достоверен. Двигается на
   каждом обычном тике трекера. Хранилище — DataStore (Room-миграция тут не нужна).
3. **Досчёт при старте контроля** (и на всякий случай раз в N минут):
   - `from = accountedUntil`, `to = now`; если разрыв меньше порога (~3 минуты) — ничего не делаем;
   - `queryEvents(from, to)` → свернуть `ACTIVITY_RESUMED`/`ACTIVITY_PAUSED` в интервалы
     «пакет X был на переднем плане», отсечь по `SCREEN_NON_INTERACTIVE`/`KEYGUARD_SHOWN`;
   - к каждому интервалу применить те же правила, что и обычный тик (`countsTowardsDailyLimit`,
     бюджет/перерасход), разложить по датам;
   - записать, сдвинуть ватерлинию.
4. **Показать факт.** Ребёнку на «Сегодня» и родителю в статистике: «пока контроль был выключен,
   засчитано N минут». Без этого досчёт выглядит как необъяснимая пропажа времени.

Побочная польза: тот же механизм закрывает штатные пробелы — телефон перезагрузился, приложение
стартовало не сразу.

### Чем это НЕ является

Это не восстановление контроля. Пока приложение мертво, ребёнок пользуется телефоном без
блокировок — досчёт лишь снимает выигрыш задним числом.

### Тесты

Чистая функция свёртки событий в интервалы (в `:core`, на своей модели событий): пустой список;
резюм без паузы до конца окна; вложенные переключения; события вне запрошенного окна; пересечение
полуночи.

### Риски

- Разрешение могут не выдать — фича молча не работает, надо явно показывать это в «здоровье».
- `GET_USAGE_STATS` слетает при полной переустановке (как и всё остальное) — учесть в мастере.
- Поведение `queryEvents` на HiOS надо проверить на живом телефоне, а не поверить документации.

## Задача 3. Серверный подметальщик: заметить молчание без родительского клиента

### Проблема

Сейчас о молчании ребёнка узнаёт **родительское приложение** (`ChildHealthChecker`, порог 40 минут
после `b44d58c`). Если приложение родителя выгружено из памяти — не узнаёт никто. 06.09 сработало
именно это: у Володи стоит сборка от 01.09 с порогом 12 часов, и уведомление не пришло.

### Что делаем на сервере

Сервер уже принимает heartbeat (`POST /device/health`, `childrenService.saveHealth`) и умеет
рассылать родителям через WebSocket (`broadcastChildHealthChanged`). Добавляем:

1. **Периодическую проверку** (таймер в процессе сервера): у кого `last_health_at` старше порога.
2. **Порог и тишина** — те же, что на клиенте: 40 минут, ночное окно 23:00–08:00 не тревожит.
   Значения в конфиг, не в код.
3. **Идемпотентность:** по одному ребёнку не чаще одного оповещения в N часов, иначе родителя
   зальёт. Нужна отметка «когда последний раз звали».
4. **Канал доставки.** WS покрывает только открытое приложение. Нужен внешний — и здесь **нужно
   решение Володи**:
   - **Telegram-бот** — проще всего, бесплатно, доходит гарантированно, но новая внешняя
     зависимость и токен в секретах;
   - **e-mail (SMTP)** — без новых аккаунтов, но легко теряется в почте;
   - **FCM** — «правильный» путь и push прямо в шторку, но требует Firebase-проекта и заметно
     больше работы на обеих сторонах.

### Тесты

Серверные тесты уже есть (`test/health-report.test.js`) — добавить на подметальщик: молчание
дольше порога зовёт один раз; повторный проход не зовёт; ночью не зовёт; пришедший heartbeat
сбрасывает состояние.

## Ход работ

### Задача 1 — сделана 06.09.2026, ветка `feature/usage-attribution`

Реализовано:

- `:core` — `ForegroundWindow.kt`: `WindowKind`, `WindowSnapshot`, чистая `resolveForegroundPackage`
  (верхнее ПРИКЛАДНОЕ окно). Тесты `ForegroundWindowTest` — 9 случаев, включая шторку и клавиатуру
  поверх игры.
- `:platform` — `KidGuardAccessibilityService`: событие `TYPE_WINDOW_STATE_CHANGED` больше не
  обновляет монитор вслепую, решение принимается по роду окна с `event.windowId`.

**Два отступления от первоначального замысла — оба выявлены при проверке на устройствах:**

1. **`ForegroundAppMonitor.clear()` не добавляли.** Планировалось обнулять передний план, когда
   прикладных окон нет. От этого отказались: `activePackage == null` означает для `shouldBlock`
   «блокировать нечего», то есть пустой пересчёт в момент переключения экранов на миг снимал бы
   блокировку. Пустой результат теперь просто не трогает монитор, а учёт в такие моменты и так
   стоит — `ScreenTimeTracker` требует включённый и разблокированный экран.

2. **Появился `shellPackages` — набор пакетов, чьи окна мы видели служебными.** Нужен для событий
   от окон, которых в стеке уже нет. Таких случая два, и они требуют противоположного: окно нового
   приложения ещё не доехало до `getWindows()` (верить событию, иначе блокировка запоздает) либо
   окно оболочки уже закрылось (верить стеку). Без этого различения при закрытии шторки systemui
   просачивался в монитор на ~50 мс — это было видно в логе на эмуляторе. Набор копится
   наблюдением, а не списком констант: на каждой прошивке оболочка называется по-своему.

Проверено на устройствах:
