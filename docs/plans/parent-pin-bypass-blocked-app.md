# План: обход блокировки «запрещённого» приложения родительским PIN

## Контекст

Родитель добавляет приложение в список «Запрещённые» (`blockedApps`). На телефоне ребёнка при
попытке его открыть `BlockingController` отправляет на домашний экран и на 6 секунд показывает
оверлей «Приложение недоступно — это приложение запретил родитель» (`OverlayManager`, окно
`TYPE_APPLICATION_OVERLAY`, автоскрытие по таймеру).

Проблема: если запрещённое приложение открывает сам родитель (пример — «Настройки», добавленные в
список, чтобы их не трогал ребёнок), у него нет способа зайти внутрь — блокировка срабатывает
одинаково для обеих ролей, потому что решение принимается по пакету, а не по тому, кто держит
телефон.

Хочется добавить на этот оверлей кнопку/ссылку «PIN родителя», по образцу уже реализованного
`PinOverlayManager` (используется для VPN/Accessibility/Device Admin/«О приложении» и для замка
«контроль отключён» — [[kidguard-control-guard-and-parent-alerts]]). Задача — переиспользовать этот
компонент, а не изобретать новый ввод PIN.

## Что переиспользуем без изменений

`PinOverlayManager` уже умеет всё, что нужно: клавиатуру, проверку через `PinGuard`, счётчик
неверных попыток, блокировку по времени, ссылку «Назад». Он не привязан к accessibility-сервису
жёстко — рисуется его окном, если сервис жив, иначе окном приложения (fallback уже есть). Значит его
можно звать прямо из `BlockingController` (он работает в foreground-сервисе), без правок самого
`PinOverlayManager`.

## Решения (обсуждено с Володей, зафиксированы финальные)

**1. Какие причины блокировки получают кнопку PIN — ВСЕ.**
Изначально предлагал ограничить только `BLOCKED_BY_PARENT`, но Володя поправил: PIN знает только
родитель, а значит ссылка должна снимать **любой** блокирующий оверлей — и `LIMIT_EXPIRED`, и
`STUDY_TIME`, и `BLOCKED_BY_PARENT`. Мотивация: родитель, взяв телефон ребёнка, должен иметь
возможность быстро снять СВОЁ ЖЕ ограничение на месте, а не лезть в своё приложение, чтобы сначала
отключить его там, а потом включить обратно. Единственное условие показа ссылки — задан ли вообще
родительский PIN (см. пункт 4), от причины блокировки это больше не зависит.

**2. Что происходит после верного PIN — автоперезапуск, подтверждено.**
Приложение уже отправлено на домашний экран (это происходит сразу, до открытия PIN-клавиатуры) —
после успешной проверки не просто скрываем оверлей, а **перезапускаем само приложение**
(`packageManager.getLaunchIntentForPackage(pkg)`), чтобы родитель не открывал его вручную заново.

**3. Насколько долго действует обход — подтверждено.**
Пока родитель не уходит из этого приложения (фон переключается на другой пакет) — без обхода по
таймеру. Реализуется сравнением текущего `activePackage` с «разблокированным» пакетом, обнуляется в
момент реального перехода на другой пакет.

**4. Если PIN не задан родителем вовсе — подтверждено, без изменений.**
Ссылка на оверлее не показывается — блокировка работает как раньше.

## Технические изменения

### `platform/overlay/OverlayManager.kt`
- `show()` получает новый необязательный параметр `onPinRequested: (() -> Unit)? = null`.
- В `createOverlayView()` — если параметр передан, под текстом добавляется текстовая ссылка (стиль
  как `buildLinkView` в `PinOverlayManager` — тот же акцентный цвет), клик сначала скрывает
  блокирующий оверлей (переиспользуя существующий `dismiss()`), потом вызывает колбэк.
- Логику «для какой причины показывать ссылку» `OverlayManager` не знает — это решает вызывающая
  сторона (`BlockingController`), передавая `onPinRequested` или `null`.

### `platform/overlay/BlockingController.kt`
- Внедряются `PinGuard` и (через уже внедрённый `policyRepository`) `pinProtection` — читаем в
  `combine`, как и остальные срезы политики.
- Новое приватное состояние: `private val bypassedPackage = MutableStateFlow<String?>(null)`.
- Перед `flatMapLatest` добавляется `onEach`, который сбрасывает `bypassedPackage` в `null`, если
  активный пакет реально сменился и не совпадает с разблокированным (обнуление обхода при уходе из
  приложения).
- В теле `combine`: `bypassActive = activePackage == bypassedPackage.value`; итоговый
  `block = !bypassActive && shouldBlock(...)` (сама чистая функция `shouldBlock` в `core` не
  меняется — обход это сессионное платформенное состояние, не часть доменного правила).
- Если `block && pinProtection != null` (причина блокировки уже не важна — снимаем PIN'ом любую) — в
  `overlayManager.show(...)` передаётся `onPinRequested`, который вызывает
  `pinOverlayManager.show(verifyPin = ::verifyPin, onUnlocked = { bypassedPackage.value = activePackage;
  relaunch(activePackage) }, onCancel = {})`.
- `relaunch(pkg)` — `getLaunchIntentForPackage` + `FLAG_ACTIVITY_NEW_TASK`.
- `verifyPin` — тонкая обёртка над `pinGuard.verify(entered)`, как в `KidGuardAccessibilityService`.

### Строки (`platform/src/main/res/values/strings.xml`)
- `overlay_pin_bypass_action` — текст ссылки на блокирующем экране, например «Открыть с PIN
  родителя» (общий для всех трёх причин — LIMIT_EXPIRED/STUDY_TIME/BLOCKED_BY_PARENT).
- `pin_overlay_bypass_subtitle` — подзаголовок PIN-клавиатуры для этого кейса, общая формулировка
  под любую причину (существующий `pin_overlay_subtitle` — «Эту настройку защитил родитель», не
  подходит по смыслу).

### Тесты
Новых unit-тестов в `core` не требуется — весь новый код платформенный (нет чистой функции,
достойной отдельного теста; `shouldBlock` не меняется). Проверка — вручную на эмуляторах.

## Проверка на эмуляторах

1. Добавить «Настройки» в «Запрещённые» → на детском эмуляторе открыть Настройки → оверлей + ссылка
   «Открыть с PIN родителя».
2. Неверный PIN — ошибка, счётчик попыток как обычно (переиспользуется существующая защита от
   перебора).
3. Верный PIN — оверлей исчезает, Настройки открываются автоматически без ручных действий.
4. Пока не выходишь из Настроек (листаешь подэкраны) — повторно PIN не спрашивается.
5. Выйти на «Домой» и открыть Настройки снова — блокировка и требование PIN возвращаются.
6. То же самое проверить для исчерпанного дневного лимита (`LIMIT_EXPIRED`) и для «Времени учёбы»
   (`STUDY_TIME`) — ссылка PIN должна сниматься и там, и приложение так же перезапускаться.
7. Если PIN у родителя не задан — ссылки нет вообще ни на одном из трёх оверлеев, поведение как до
   этой фичи.

## Ограничения (фиксирую, не решаю здесь)

Обход — только в памяти работающего `BlockingController` (не персистится). Переживёт обычное
использование, но не переживёт `force-stop`/перезапуск сервиса — это ожидаемо и безопасно (после
перезапуска блокировка просто снова активна, PIN нужен заново).
