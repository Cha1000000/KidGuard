# План: бонус не должен гаситься перерасходом

## Симптом (наблюдение Володи, 05.08.2026)

У Олега дневной лимит 3 ч. Он его израсходовал, а потом продолжил пользоваться телефоном
(смахнув блокирующий оверлей) — статистика показала 3 ч 47 мин. Родитель выдал бонус 30 мин —
**блокировка не снялась**. После второй выдачи 30 мин ребёнок получил 6 мин
(60 − 47). Чтобы дать реальные 30 минут, пришлось нажать кнопку три раза.

Ожидаемое поведение: если время уже вышло, выданный бонус снимает блокировку **немедленно**,
и отсчёт этих минут идёт **с момента выдачи**, а не гасит задним числом то, что ребёнок
«накрутил» после блокировки.

## Причина

Счётчик израсходованного (`screen_time.seconds`) продолжает расти и после того, как бюджет
исчерпан: `ScreenTimeTracker` тикает всегда, когда экран включён, разблокирован и не закрыт нашим
блокирующим UI (`ScreenTimeTracker.kt:83`). Оверлей мягкой блокировки смахивается — значит время
идёт дальше и записывается в тот же счётчик.

Остаток же считается как «бюджет минус израсходовано»:

```kotlin
// ObserveLimitStateUseCase.kt:53
val minutesLeft = (limitMinutes + bonusMinutes) - usedMinutes
```

Поэтому первые минуты любого бонуса уходят на погашение накопленного «долга». Ровно та же
формула — и та же болезнь — у личных лимитов приложений (`ObserveAppLimitStateUseCase.kt:45`):
бонус приложению сперва гасит перерасход по этому приложению.

## Решение: развести бюджет и перерасход по разным счётчикам

Один счётчик сегодня отвечает на два разных вопроса — «сколько бюджета израсходовано» и «сколько
ребёнок пробыл в телефоне». Разводим их:

- пока бюджет не исчерпан — тик идёт в **бюджетный** счётчик (как сейчас);
- как только исчерпан — тик идёт в отдельный счётчик **перерасхода**.

Тогда бюджетный счётчик никогда не превышает бюджет, и `бюджет − израсходовано` после выдачи
30 минут даёт ровно 30 минут. **Формулы остатка при этом не меняются вообще** — они начинают
работать правильно сами.

Перерасход не теряется: он остаётся отдельной величиной и по-прежнему виден в статистике —
родительский экран покажет тот же перерасход, что и сейчас (см. «Синхронизация» ниже).

Это же решение закрывает и лимиты приложений — тем же приёмом, вторым счётчиком на пакет.

## Правки по слоям

### 1. Room: v11 → v12 (`:data`)

Две колонки, обе `NOT NULL DEFAULT 0` — старые строки читаются как «перерасхода не было»:

```sql
ALTER TABLE screen_time     ADD COLUMN overrunSeconds INTEGER NOT NULL DEFAULT 0;
ALTER TABLE app_screen_time ADD COLUMN overrunSeconds INTEGER NOT NULL DEFAULT 0;
```

`MIGRATION_11_12` — в `Migrations.kt` по образцу соседних, регистрация в `DatabaseModule`.
Поля добавляются в `ScreenTimeEntity` и `AppScreenTimeEntity`.

Сброс дневного лимита (`resetScreenTime` / `resetAppScreenTime`) удаляет строки целиком, поэтому
перерасход обнуляется вместе с расходом — отдельных правок не требует.

### 2. `UsageRepository` (`:core` + `:data`)

Добавляются:

```kotlin
/** Время сверх исчерпанного дневного бюджета (секунд): бюджет им уже не расходуется. */
fun overrunSeconds(date: LocalDate): Flow<Int>
suspend fun addOverrunTime(date: LocalDate, seconds: Int)

/** Время сверх исчерпанного ЛИЧНОГО лимита приложения: пакет → секунды. */
fun appOverrunByPackage(date: LocalDate): Flow<Map<String, Int>>
suspend fun addAppOverrunTime(date: LocalDate, packageName: String, seconds: Int)

/** Фактическое время в приложениях = бюджетное + перерасход. Для статистики. */
fun appTotalScreenTimeByPackage(date: LocalDate): Flow<Map<String, Int>>
```

`appTotalScreenTimeByPackage` — отдельный метод, а не изменение семантики существующего:
у `appScreenTimeByPackage` шесть потребителей, и половине нужен именно бюджетный расход (остаток
лимита), а половине — фактическое время (статистика). Явные имена дешевле, чем ловить потом,
где сложили, а где забыли. KDoc интерфейса переписывается под три вида счётчиков.

### 3. Куда писать тик — чистая функция в `:core`

Решение вынести из `ScreenTimeTracker` в `:core` рядом с `countsTowardsDailyLimit` — там же, где
живут остальные правила, и там же, где есть тесты (в `:platform` тестового сорсета нет):

```kotlin
enum class UsageBucket { BUDGET, OVERRUN }

/** Куда записать тик. dailyBucket = null — приложение дневной лимит не расходует. */
data class UsageTickTargets(val dailyBucket: UsageBucket?, val appBucket: UsageBucket)

fun usageTickTargets(
    countsTowardsDailyLimit: Boolean,
    dailyLimitState: LimitState,
    appLimitState: LimitState
): UsageTickTargets
```

Комбинаций восемь, и перепутать их легко — поэтому таблица покрывается unit-тестом
(`UsageTickTargetsTest`), как `BlockingDecisionTest` и `CountsTowardsDailyLimitTest`.

### 4. `ScreenTimeTracker` (`:platform`)

В тике сперва читаются оба состояния лимита (`ObserveLimitStateUseCase` и
`ObserveAppLimitStateUseCase(activePackage)` через `.first()`), затем — по `usageTickTargets` —
пишется в бюджетный счётчик или в перерасход. Порядок важен: читаем до записи, иначе собственный
тик сдвинет состояние.

Использование готовых use case'ов, а не своей копии формулы, — чтобы «исчерпан» в учёте и
«исчерпан» в блокировке не разъехались: это ровно то, из-за чего появился этот баг.

### 5. Синхронизация ребёнок → родитель (`SyncRepositoryImpl.pushUsage`)

Сервер и протокол **не трогаем**: `UsageEntryDto` уже использует `packageName = ""` как маркер
«итог за день», валидации имени пакета на сервере нет (`usageService.isValidBatch`). Добавляем
второй маркер в том же духе — константа в `:core` рядом с `UsageEntry`:

```kotlin
const val OVERRUN_PACKAGE = "__overrun__"
```

- итог за день (`packageName = ""`) — бюджетный расход, как и раньше;
- новая запись с `packageName = "__overrun__"` — перерасход за день;
- пер-app записи отправляются **суммой** (`appTotalScreenTimeByPackage`): родителю нужно
  фактическое время в приложении, а не бюджетная его часть.

### 6. Статистика родителя (`StatisticsViewModel`)

- «время, расходующее лимит» за день = запись-итог + запись-перерасход. После сложения все
  существующие вычисления работают как раньше: `dailyBudgetState` увидит тот же перерасход, что и
  до правки, график «Последние 7 дней» — те же столбики. Правка на несколько строк;
- маркер `__overrun__` исключается из `todayAppEntries`, иначе он появится в списке
  «По приложениям» отдельной строкой. `StatisticsViewModel` — единственный потребитель
  `getChildUsage`, так что фильтр нужен ровно в одном месте.

### 7. Детские экраны

- `TodayViewModel`: «всё экранное время» (карточка «Сегодня») считается по
  `appTotalScreenTimeByPackage`; кольцо остатка остаётся на бюджетном счётчике — оно и станет
  правильным само;
- `ChildTodayStatsViewModel`: крупная цифра, доли и список приложений — по
  `appTotalScreenTimeByPackage`;
- `ChildLimitedAppsViewModel` и `TodayViewModel.computeRules` (остаток по приложению) остаются на
  бюджетном счётчике — им нужен именно он;
- `AppLimitsViewModel` (родитель, «сколько сегодня использовано» рядом с лимитом) — фактическое
  время, `appTotalScreenTimeByPackage`.

## Что НЕ меняется

- формулы остатка (`ObserveLimitStateUseCase`, `ObserveAppLimitStateUseCase`, `dailyBudgetState`)
  и их тесты;
- «Заблокировать на сегодня» (`applyDailyBlock`) — выставляет бюджетный расход в `лимит + бонус`,
  остаток становится 0; перерасход на это не влияет;
- сервер KidGuard-server — ни схемы, ни кода, ни деплоя.

## Проверка

1. `./gradlew :core:test :app:assembleDebug` — включая новый `UsageTickTargetsTest`.
2. На связке эмуляторов (родитель + ребёнок):
   - лимит 5 мин, дождаться блокировки, смахнуть оверлей, накрутить ~3 мин перерасхода;
   - выдать бонус 5 мин → **блокировка снимается сразу**, на детском экране «Сегодня» остаток
     ровно 5 мин (а не 2);
   - убедиться, что через 5 минут использования блокировка возвращается;
   - у родителя на «Статистике»: экранное время за сегодня включает перерасход, столбик и подпись
     перерасхода те же, что до правки;
   - то же для личного лимита приложения (лимит 2 мин на приложении, перерасход, бонус 5 мин);
   - «Сбросить сегодняшний лимит» обнуляет и перерасход;
   - «Заблокировать на сегодня» по-прежнему обнуляет остаток.
3. Обновление поверх старой версии (`adb install -r`) — БД мигрирует, накопленные за день цифры
   на месте.

## Известные ограничения

- Перерасход, накопленный **до** обновления, останется в бюджетном счётчике (разделить его задним
  числом нечем). На детском телефоне это лечится кнопкой «Сбросить сегодняшний лимит» или
  наступлением следующего дня.
- Перерасход возникает только потому, что оверлей мягкой блокировки смахивается. Кастомный
  lock-экран остаётся в бэклоге — он убрал бы саму возможность накрутить время сверх лимита.
