# Обход PIN-замка списка последних: исправление в три слоя

**Статус:** реализовано (ветка `feature/recents-pin-bypass-fix`), проверено на эмуляторах; ждёт приёмки и проверки поворотного пути на телефоне Олега
**Ветка (при реализации):** `feature/recents-pin-bypass-fix`
**Заведён:** 2026-09-15

## Что случилось

На телефоне Олега с 10.09 контроль убивали семь раз (`USER REQUESTED / STOP APP`), в обход
PIN-замка на экране списка последних. 15.09 без контроля ушло оценочно около пяти часов, из них
около трёх — во «Время учёбы». Воспроизведено вместе с Володей, путей два:

1. **Из горизонтальной игры.** Brawl Stars → «Домой» → обзор. PIN-экран появляется **на секунду и
   исчезает**; через 1–2 секунды обзор открыт без замка, «Очистить всё» доступна. С рабочего стола
   PIN стоит.
2. **Через «Меню спец. возможностей»** (нашёл Володя). Системная служба
   `com.android.systemui.accessibility.accessibilitymenu/…AccessibilityMenuService` с кнопкой на
   панели навигации; в её меню есть действие «Недавние приложения». Обзор открывался без PIN.
   Володя службу выключил, но вернуть её можно, если контроль снова умрёт и настройки останутся
   без защиты.

## Корень

В `KidGuardAccessibilityService` PIN-оверлей снимается при **любом** не-критичном событии окна от
пакета, которого нет среди хостов оверлея. Для обзора хост — только лаунчер:

```kotlin
val overlayHosts = if (pinOverlayScreen == CriticalScreen.RECENTS) launcherPackages else overlayHostPackages
if (packageName != applicationContext.packageName && packageName !in overlayHosts) {
    if (pinOverlayManager.isShowing()) pinOverlayManager.hide() ...
}
```

- При входе в обзор из горизонтального приложения экран поворачивается в портрет: пересоздаются
  окна `com.android.systemui` (панель навигации, строка состояния), шлёт событие и сама игра.
  Правило принимает это за «ребёнок ушёл в другое приложение» и снимает замок.
- Панель «Меню спец. возможностей» — тоже окно `systemui`. Вероятно, срабатывает то же правило.
  **Не проверено отдельно** — проверить после исправления.

Попутно выяснилось: список окон у сервиса доступности **запаздывает**. В момент обзора
`dumpsys accessibility` показывал верхним окном «Brawl Stars» 2460×1080, хотя на экране был лаунчер
в портрете. Поэтому проверку «действительно ли ребёнок ушёл» нельзя строить только на этом списке —
её обманет тот же поворот.

## Слой 1 — PIN обзора снимается только по решению, а не по событию (все телефоны)

**Главное исправление; закрывает причину смертей контроля на любом устройстве.**

Пока показан PIN для `RECENTS`, общее правило «убрать оверлей при уходе» к нему **не применяется**.
Оверлей уходит только тремя путями:

1. **Верный PIN** — как сейчас: обзор уже открыт, родитель разбирает карточки.
2. **Отказ** («Назад» на оверлее) — как сейчас: `GLOBAL_ACTION_HOME`, игнор хвоста событий.
3. **Входящий или активный звонок** — единственное внешнее исключение. Звонок нельзя закрывать
   PIN-экраном: ребёнок должен иметь возможность ответить. Состояние звонка берём у телефонии
   (`TelephonyManager` / `TelephonyCallback`), а не по пакету окна: пакет звонилки на прошивках
   разный, а событие о звонке однозначно. При снятии из-за звонка обзор за оверлеем уже не
   открыт — звонок перекрывает всё.

**Почему не «снимать при подтверждённом уходе через паузу».** Рассматривался вариант: на чужое
событие не снимать сразу, а через ~1,5 с проверить верхнее окно по `getWindows()`. Отвергнут,
потому что список окон у сервиса запаздывает (см. «Корень») — после поворота он показывал игру.
Пауза лишь сдвинула бы окно уязвимости, но не закрыла бы его. Модальный оверлей, который снимается
только по решению человека или по звонку, проще и честнее.

**Чем рискуем.** Если ребёнок каким-то образом окажется в другом приложении, пока висит PIN, оверлей
останется над этим приложением до «Назад». Это ровно то поведение, которое нужно от замка: выход —
через «Назад».

**Реализация:**
- Решение «снимать ли PIN обзора» вынести в чистую функцию в `:core` (по образцу `shouldBlock`):
  входы — экран оверлея, пакет события, признак звонка; выход — снимать/не снимать. Покрыть
  юнит-тестами: поворот (systemui), событие игры, событие лаунчера, наше окно, звонок; для
  остальных критичных экранов — прежнее поведение (регрессия).
- В сервисе — подписка на состояние звонка, снятие оверлея обзора при звонке.
- Остальные критичные экраны (настройки, VPN, «О приложении») **не меняем**: у них хост — сами
  настройки, и прежнее правило работает. Если окажется, что поворот ломает и их, — отдельной задачей.

## Слой 2 — сторож чужих служб доступности (телефоны с `WRITE_SECURE_SETTINGS`)

**Страховка на случай, если меню снова включат, пока контроль жив.** На телефоне Олега у KidGuard
выдано `WRITE_SECURE_SETTINGS` (granted=true) — им же `AccessibilityGuardController` уже возвращает
отключённый KidGuard.

- Встраивается в существующий цикл `AccessibilityGuardController`, плюс `ContentObserver` на
  `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`, `ACCESSIBILITY_BUTTON_TARGETS` и
  `ACCESSIBILITY_SHORTCUT_TARGET_SERVICE` — чтобы реагировать сразу, а не на следующем тике.
- **Гасим только известные опасные службы** — меню с действием «Недавние приложения»:
  - `com.android.systemui.accessibility.accessibilitymenu/…AccessibilityMenuService` (HiOS/AOSP);
  - `com.google.android.marvin.talkback/com.google.android.accessibility.accessibilitymenu.AccessibilityMenuService`
    (меню из Android Accessibility Suite).

  Их убираем из `ENABLED_ACCESSIBILITY_SERVICES`, `ACCESSIBILITY_BUTTON_TARGETS` и
  `ACCESSIBILITY_SHORTCUT_TARGET_SERVICE`, **не трогая KidGuard и всё остальное**.
- **Все прочие чужие службы не трогаем**, только сообщаем родителю (слой 3). Решение от 15.09: гасить
  всё подряд нельзя — ребёнку может понадобиться, например, TalkBack.
- Без `WRITE_SECURE_SETTINGS` слой молча не работает: остаются слой 1 и оповещение родителя.

## Слой 3 — родитель узнаёт о чужих службах доступности (все телефоны)

- `DeviceHealth` получает список включённых **посторонних** служб доступности (всё, кроме KidGuard)
  с признаком «опасная» (из того же списка, что в слое 2). Сервер хранит отчёт непрозрачно —
  серверных правок нет; изменение списка само шлёт родителю WS-сигнал.
- **Опасная служба включена** — это поломка: красная плашка на карточке «Дети» и пункт в листе
  здоровья («Включено меню спец. возможностей — через него открывают список приложений в обход
  замка»). Если сторож слоя 2 её погасит, плашка сама уйдёт со следующим отчётом; если прав нет —
  висит, пока родитель не выключит вручную.
- **Прочая чужая служба** — не поломка, но информация в листе здоровья («Включены посторонние
  службы доступности: …»), без красной плашки.
- Отчёт отправляется немедленно при изменении списка (`HealthReportTrigger`), а не через 15 минут.
- Поля DTO — с дефолтами (старые сборки на телефонах).

## Порядок и проверка

1. Слой 1: чистая функция + тесты → сервис → звонок.
2. Слой 3 (модель и отчёт) — до слоя 2, чтобы проверять сторож по уже видимому родителю статусу.
3. Слой 2: сторож + наблюдатель настроек.
4. **Проверка на эмуляторе:** горизонтальное приложение → «Домой» → обзор → PIN стоит; звонок
   (`adb emu gsm call`) снимает PIN; включение меню доступности → сторож выключает, родитель видит.
5. **Проверка на телефоне Олега** — только с участием Володи: из горизонтальной игры в обзор (PIN
   должен стоять); включить меню спец. возможностей и проверить, что сторож его гасит и его действие
   «Недавние» тоже упирается в PIN. «Очистить всё» не нажимаем.
6. Юнит-тесты всех модулей, тесты миграций (если понадобятся), ревью перед мёржем.

## Открытые вопросы

- **Имя окна меню доступности на HiOS** не снято. Для слоя 1 не нужно (снимать PIN по чужим событиям
  перестаём вовсе), но пригодится для диагностики.
- **Как ребёнок вернул контроль к жизни между смертями** — только открытием приложения KidGuard.
  Вопрос «почему контроль сам не поднимается после force-stop» этим планом не решается: против
  force-stop нет программного лекарства; план убирает сам способ его вызывать.

## Итоги реализации (15.09.2026)

Все три слоя написаны, 308 юнит-тестов и 6 тестов миграций зелёные. **Не закоммичено** — жду «ок».

**Слой 1** — PIN обзора снимается только по решению (верный PIN / отказ) или звонку. Чистая функция
`shouldDismissPinOverlayOnWindowEvent` + `shouldDismissRecentsPinOnCall` в `:core`, 9 тестов. Звонок —
через общий помощник `Context.callAudioModeFlow` (вынесен из ночного замка, тот переведён на него же).

**Слой 2** — сторож опасных служб в `AccessibilityGuardController`: `ContentObserver` на три ключа
настроек + вычистка на каждом тике. `PermissionsManager.disableRiskyAccessibilityServices`,
модель `RiskyAccessibilityServices` (6 тестов). **Проверено вживую на эмуляторе:** включённое «Меню
спец. возможностей» и его кнопка выключаются за секунды, в логе `Выключено опасное меню`.

**Слой 3** — `DeviceHealth.foreignAccessibilityServices`; опасная служба делает отчёт нездоровым.
Плашка «Включено меню спец. возможностей» на «Дети», строки в листе здоровья, отдельный текст
уведомления, учёт в `childAlert` (4 теста) и в снимке тревог. **Проверено вживую:** heartbeat с
посторонней службой (TalkBack) доезжает до родителя, ложной плашки нет.

### Что проверено на эмуляторе и что осталось на телефон

- **Слой 2 (меню) — воспроизведён полностью** на эмуляторе.
- **Слой 1 (поворот из игры) на эмуляторе не воспроизводится:** обзор на Pixel всегда портретный,
  события поворота от игры нет — это специфика HiOS. Косвенно подтверждено логом: PIN обзора висит
  и не снимается событиями лаунчера. **Прямую проверку поворотного пути делать на телефоне Олега
  вместе с Володей** (из горизонтальной игры «Домой» → обзор → PIN должен стоять). «Очистить всё»
  не нажимаем.

# Доработка: PIN обзора иногда НЕ показывается (15.09.2026)

Проверка слоя 1 на телефоне Олега выявила **вторую, отдельную дыру**: слой 1 держит уже
показанный PIN (доказано кадрами 18:21:16–18), но PIN иногда **не показывается вовсе**, и обзор
открывается без замка. По логам сервиса — одна явная причина и одна под вопросом.

## Причина 1 (подтверждена) — окно игнора после отказа

После отказа от PIN (`onCancel`) ставится `recentsIgnoredUntil = now + RECENTS_SETTLE_MS` (1200 мс),
и всё это время recent-события пропускаются:
```
18:25:04  Заголовок: hios launcher recent apps
18:25:04  Критичный экран RECENTS — показываю PIN-оверлей
18:25:04  Список последних только что закрыли — пропускаю событие   ← PIN не показан
```
Окно задумано, чтобы погасить «хвост» — лишнее recent-событие, которое лаунчер шлёт сразу после
нашего `GLOBAL_ACTION_HOME`. Побочка: **осознанный быстрый повторный вход** в обзор (Назад → снова
обзор, или Назад → игра → обзор) попадает в те же 1200 мс и проходит без PIN. Таймер не различает
хвост от намеренного входа.

### Исправление 1

Заменить таймер на условие «ждём реального ухода из обзора». Пропускать recent-события не N мс, а
**пока пользователь фактически не покинул обзор** — не пришло событие прикладного окна (игра) или
домашнего экрана. Как только увидели такой уход — флаг снят, и следующий вход в обзор
перехватывается сразу.

- Хвост приходит подряд с обзором, без промежуточного ухода → по-прежнему гасится.
- Намеренный повторный вход всегда идёт после ухода (домой/в игру) → флаг уже снят → PIN покажется.
- Возможная плата: если хвост придёт уже ПОСЛЕ того, как система показала домашний экран, флаг
  окажется снят и хвост даст лишний короткий PIN на рабочем столе. Лишний PIN безопаснее
  пропущенного, и слой 1 его корректно удержит/снимет по «Назад».

Флаг снимается в обработчике события, когда экран — не обзор (прикладное окно или домашний лаунчер).

## Причина 2 (под вопросом) — заголовок «главный экран» вместо «recent apps»

```
18:25:11  (система) onStartRecentsAnimation → QuickstepLauncher
18:25:12  Заголовок: hios launcher главные экран 1 из 2   ← детект RECENTS не сработал
```
`detectCriticalScreen` распознаёт обзор ТОЛЬКО по заголовку окна (`RECENTS_KEYWORDS`), а здесь
пришёл заголовок домашнего экрана. Но `RecentsAnimation` в HiOS анимирует и **закрытие** обзора
(уход домой) — этим тем же обработчиком, так что «главный экран» здесь, скорее всего, закрытие
обзора, а не открытие, и детект отработал верно.

### Подход к причине 2

Не усложнять вслепую. Сначала внедрить исправление 1 и проверить на телефоне Олега. Если
нестабильность исчезла — причина 2 была ложной (это было закрытие обзора). **Если PIN всё ещё
иногда не показывается** — добавить второй сигнал детекта обзора, не завязанный на заголовок:
по содержимому окна лаунчера (карточки приложений / кнопка «Очистить всё» в дереве узлов, по
образцу `awaitOwnAppScreen`). Добавлять только по факту, чтобы не ловить домашний экран как обзор.

## Проверка

1. Исправление 1 → сборка → телефон Олега (вместе с Володей): обзор → Назад → снова обзор (и
   вариант с игрой между) — PIN должен появляться КАЖДЫЙ раз. Серия кадров + лог сервиса.
2. Если осталось — исправление 2, повтор.
3. Юнит-тесты на логику «ждём ухода» (что выносимо в чистую функцию). Регрессия остальных
   критичных экранов — их settle не касается.

# Итог доработки (15.09.2026, проверено на телефоне Олега)

Проверка вскрыла, что стабильного показа PIN мало — важна СКОРОСТЬ. Ребёнок жал «Очистить всё» в
окно между открытием обзора и появлением замка. Закрыто четырьмя правками:

1. **Слой 1** (не снимать показанный PIN чужим событием) — верный, оставлен.
2. **Подавление «хвоста» после отказа убрано совсем.** Вариант с флагом «жду ухода» не сработал:
   HiOS не шлёт событие домашнего экрана, флаг зависал и глушил осознанный повторный вход. Лишний
   короткий PIN после «Назад» — безопасная косметика.
3. **Окно разблокировки 120 с → 20 с** (как у прочих критичных экранов; решение Володи).
4. **Задержка показа устранена** — главное:
   - убрано чтение `pinProtection` из DataStore на горячем пути, наличие PIN кешируется
     (`@Volatile pinConfigured`), путь RECENTS синхронный;
   - `PinOverlayManager.show`/`hide` больше не через `mainHandler.post`, а синхронно на главном
     потоке (`runOnMain`). Замер до правки: показ вставал в очередь за анимацией обзора на
     400–680 мс; после — мгновенно.

**Итог на телефоне Олега:** до ускорения ребёнок стабильно успевал «Очистить всё» (смерти контроля
в `exit-info` 18:48–19:00); после — успеть уже нельзя, замок закрывает раньше, за 2 минуты активных
попыток ни одной смерти.

Осталось на потом (не блокирует): косметика мелькания PIN на рабочем столе после «Назад».

**Готово к финальному прогону тестов и мёржу** ветки `feature/recents-pin-bypass-fix`.
