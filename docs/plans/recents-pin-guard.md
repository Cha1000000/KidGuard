# Список последних приложений под PIN

Дата: 06.09.2026. Ветка: `feature/recents-pin-guard`.

## Зачем

По `dumpsys activity exit-info` на телефоне Олега **все** смерти контроля идут одним путём: кнопка
«Очистить всё» в списке последних приложений (см.
[usage-accuracy-and-control-recovery.md](usage-accuracy-and-control-recovery.md)). Не вендорский
киллер, не OOM, не «Остановить» в настройках — те двери либо закрыты PIN-ом, либо ни разу не
сработали.

Замок на карточке эту дверь не закрывает: «Очистить всё» на HiOS работает в две фазы, и вторая
делает force-stop всему фону независимо от замков. Досчёт времени (задача 2) выигрыш от убийства
снимает, но пользоваться телефоном, пока контроль мёртв, не мешает. Значит саму дверь надо закрыть.

## Как это должно работать (ТЗ Володи, 06.09.2026)

Не просто уводить ребёнка с экрана, а сделать список последних доступным родителю:

1. Ребёнок открывает список последних → экран **сворачивается**, поверх показывается PIN-оверлей.
2. Оверлей смахнули/нажали «Назад» → список последних **не показывается**, остаёмся там, где были.
3. Введён верный родительский PIN → список последних **открывается снова**, и родитель спокойно
   разбирает свёрнутые приложения.

Порядок действий в реализации пришлось развернуть (см. «Перехват»), но наблюдаемое поведение
получилось ровно такое: отказался от PIN — списка не увидел, ввёл PIN — разбирает карточки.

## Что установлено на живом телефоне (06.09.2026)

Детект возможен и ложится в существующий механизм. При открытии списка последних приходит
`TYPE_WINDOW_STATE_CHANGED`, и заголовок окна прямо говорит, что это:

```
D/KidGuardA11y: Активное приложение: com.transsion.hilauncher
D/KidGuardA11y: Заголовок окна [com.transsion.hilauncher]: hios launcher recent apps
```

Проверено четырьмя открытиями подряд — заголовок стабилен. Важно, что активность при этом **не
меняется**: `mCurrentFocus` остаётся `QuickstepLauncher`, то есть по классу активности список
последних от домашнего экрана не отличить. Заголовок окна — единственный надёжный признак, и это
ровно тот источник, на котором уже держится [detectCriticalScreen].

## Реализация

### 1. Детект

Новый `CriticalScreen.RECENTS`. Условие: заголовок окна содержит одно из ключевых слов **И** пакет
события — текущий домашний лаунчер.

Ключевые слова (кросс-вендорно, набор заведомо неполон и дополняется по факту):
`recent apps`, `recents`, `overview`, `недавние`, `последние`.

Проверка пакета обязательна: слово «recent» встречается и в заголовках настроек («Недавно
открытые»), а лаунчер мы и так уже резолвим (`AlwaysAllowedPackages` / `resolveActivity(HOME)`).

### 2. Перехват

```
pinOverlayManager.show(
    onUnlocked = { /* ничего: список уже открыт, оверлей просто уходит */ },
    onCancel   = { performGlobalAction(GLOBAL_ACTION_HOME) }   // отказался — списка не увидел
)
```

**Схема изменилась по итогам проверки на эмуляторе.** Замысел был обратным: сначала закрыть список,
потом показать оверлей. Так не работает — лаунчер остаётся в режиме списка, и после закрытия
оверлея система показывает его снова. Проверены `GLOBAL_ACTION_BACK`, `GLOBAL_ACTION_HOME` и пауза
между действием и показом оверлея: во всех вариантах после отказа от PIN экран возвращался к
карточкам.

Работающая схема проще и без гонок: оверлей показывается сразу, а уводим в момент ОТКАЗА. Результат
для пользователя тот же, что в ТЗ: отказался — списка не увидел, ввёл PIN — разбирает карточки
(причём переоткрывать их не нужно, они уже перед ним).

Пока оверлей висит, карточки просвечивают сквозь него, но нажать на них нельзя — окно перехватывает
касания. Вопрос к Володе: делать ли фон для этого случая плотнее.

### 3. Окно разблокировки

`lastUnlockedAt[RECENTS]` + своя константа. Без него список, оставшийся открытым после верного PIN,
перехватился бы повторно на первом же событии окна.

Кроме того, понадобился синхронный флаг `recentsInterceptRunning`: показ оверлея идёт через
`mainHandler`, и второе событие о списке (его шлёт лаунчер, когда поверх появляется наше окно)
успевало проскочить между вызовом `show()` и фактическим показом.

Значение — **2 минуты** (`RECENTS_UNLOCK_WINDOW_MS`, согласовано с Володей). Общие 20 секунд
остальных экранов не трогаем: там они уместны — успеть довести одну настройку.

### 4. Если PIN не задан

Не перехватываем — как и на остальных критичных экранах. Иначе на непривязанном телефоне ребёнок
остался бы без списка последних вовсе.

## Риски и чем платим

- **Ребёнок теряет переключение между приложениями через список последних.** Останется домашний
  экран. Это осознанная цена, Володя её принял.
- **Гонка.** Между открытием списка и появлением оверлея проходит время доставки события
  (`notificationTimeout=100`) плюс отрисовка окна. Олег 06.09 уложился от открытия списка до
  нажатия «Очистить всё» в ~1 секунду, так что запас есть, но он не бесконечен.
- **Карточки просвечивают** сквозь полупрозрачный оверлей, пока он висит. Нажать на них нельзя,
  но видно, что за ними. Плотность фона — вопрос к Володе.
- **Жест «последние приложения» на HiOS** может открывать список без смены окна — проверить на
  телефоне после реализации, что событие приходит и на жест, а не только на кнопку.
- **Список последних — часть лаунчера**, который у нас в `alwaysAllowed`. Перехват идёт мимо
  `blockedApps` (через `detectCriticalScreen`), так что конфликта нет: домашний экран остаётся
  доступен, закрывается только режим списка.

## Проверка

На телефоне Олега:

1. Открыть список кнопкой → список свернулся, виден PIN-оверлей.
2. Смахнуть оверлей → список не появился, остались на прежнем экране.
3. Открыть снова, ввести верный PIN → список открылся, карточки смахиваются.
4. Открыть жестом (свайп снизу с задержкой) → тот же перехват.
5. `dumpsys activity exit-info` через несколько дней — новых `USER REQUESTED` быть не должно.

## Проверено (06.09.2026)

На эмуляторе (Pixel Launcher, заголовок «недавние приложения»):

- открытие списка → PIN-оверлей поверх карточек, нажать на них нельзя;
- отказ от PIN → домашний экран, карточек нет;
- повторное событие о списке отсекается флагом, экран не «дёргается».

На телефоне Олега (HiOS 14, заголовок «hios launcher recent apps») — Володя проверил вручную:
сценарий с верным PIN работает, список открывается и карточки смахиваются.

Решения по итогам: **фон оверлея оставляем как есть** — карточки просвечивают, но недоступны, и
этого достаточно.

**Не проверено:** открытие списка жестом (свайп снизу с задержкой) на HiOS. Если жест идёт мимо
`TYPE_WINDOW_STATE_CHANGED`, перехват на него не сработает — смотреть при следующей диагностике
телефона.
